ระบบเตรียมสอบ Midterm

วิชา Software Engineering (อิงตามสไลด์ Ch 1-6 และรีวิวข้อสอบจริง)

แพลตฟอร์มนี้ถูกสังเคราะห์ขึ้นเพื่อช่วยให้คุณโฟกัสเฉพาะจุดที่ออกสอบ ลดเวลาอ่านน้ำ และเพิ่มเวลาทำความเข้าใจเนื้อหาหลัก โดยแบ่งเนื้อหาตามแนวข้อสอบที่หลุดออกมา

โฟกัสข้อสอบจับคู่

  • ประเภทของ Software (ระวังชื่อโปรแกรมแปลกๆ)
  • Methodology (ข้อจำกัดงานไหนเหมาะกับ Model ไหน)
  • คุณสมบัติ Software Quality (จำนิยามอังกฤษ)
  • จุดตาย: Static Testing = Verification / Validation?

โฟกัสข้อสอบเขียนตอบ

  • บทบาท Project Manager ทำให้โปรเจกต์สำเร็จได้อย่างไร? (ใช้หลัก Quality, Cost, Delivery)
  • การเขียน Functional Requirement (FR) และ Non-Functional Requirement (NFR) จากโจทย์ CS-Hospital

1. ประเภทของ Software

แนวข้อสอบ (Matching):

ข้อสอบจะมีชื่อโปรแกรมมาให้ แล้วให้จับคู่ว่าเป็น Software ประเภทใด บางโปรแกรมอาจไม่เคยได้ยินชื่อ ให้ใช้วิธีเดาจากบริบทของการใช้งาน

Type 1

System Software

ซอฟต์แวร์ระบบ โปรแกรมที่เขียนมาเพื่อบริการโปรแกรมอื่น เกี่ยวข้องกับการจัดการทรัพยากรฮาร์ดแวร์โดยตรง

ตัวอย่างในข้อสอบ:

Windows, Linux, macOS, Compiler (GCC), Device Drivers, Task Manager

Type 2

Application Software

แอปพลิเคชันซอฟต์แวร์ โปรแกรมที่แก้ปัญหาเฉพาะทาง หรือใช้ในระบบธุรกิจ (Business System)

ตัวอย่างในข้อสอบ:

โปรแกรมบัญชีบริษัท (Accounting System), ระบบจัดการสินค้าคงคลัง (Inventory), ระบบ HR

Type 3

Engineering & Scientific

ซอฟต์แวร์ทางวิศวกรรมและวิทยาศาสตร์ เน้นอัลกอริทึมคำนวณตัวเลขมหาศาล (Number crunching) การจำลอง (Simulation) หรือออกแบบ

ตัวอย่างในข้อสอบ:

AutoCAD, MATLAB, SPSS, ซอฟต์แวร์พยากรณ์อากาศ, ซอฟต์แวร์จำลองดาราศาสตร์

Type 4

Embedded Software

ซอฟต์แวร์สมองกลฝังตัว ฝังอยู่ในอุปกรณ์หรือผลิตภัณฑ์เพื่อควบคุมฟังก์ชันเฉพาะอย่าง (ไม่มี Interface หรือมีจำกัดมาก)

ตัวอย่างในข้อสอบ:

ซอฟต์แวร์ควบคุมไมโครเวฟ, ระบบเบรก ABS ในรถยนต์, ซอฟต์แวร์ในสมาร์ทวอทช์รุ่นพื้นฐาน, ระบบไฟจราจร

Type 5

Product-line Software

ซอฟต์แวร์สายผลิตภัณฑ์ ทำมาเพื่อตลาดมวลชน (Mass market) ทำซ้ำๆ ขายให้คนทั่วไปใช้งานได้เหมือนๆ กัน

ตัวอย่างในข้อสอบ:

Microsoft Office (Word, Excel), Adobe Photoshop, เกมเมนสตรีมทั่วไป

Type 6

Web-based Software

เว็บแอปพลิเคชัน (WebApps) เว็บเพจที่รวมเอาซอฟต์แวร์ที่มีคำสั่งประมวลผลได้ เช่น HTML, CGI, Java

ตัวอย่างในข้อสอบ:

Internet Banking, E-commerce (Shopee/Lazada), Web Mail (Gmail)

Type 7

Artificial Intelligence Software

ซอฟต์แวร์ AI ใช้ Non-numerical algorithms แก้ปัญหาซับซ้อน เช่น Expert Systems, Knowledge-based System, Image/Voice Pattern Recognition, Artificial Neural Network

ตัวอย่างในข้อสอบ:

แชทบอต, ระบบจดจำใบหน้า/เสียง, ระบบแนะนำสินค้า (Recommendation)

Type 8

Mobile Application

แอปสำหรับอุปกรณ์ไร้สายขนาดเล็ก (Smartphone/Tablet) แบ่งเป็น Web-based, Native (สร้างเฉพาะ Platform) และ Hybrid (ผสมทั้งสองแบบ)

ตัวอย่างในข้อสอบ:

Mobile Banking, LINE, Grab

เสริม Ch1: Law of Software Evolution (ทฤษฎีวิวัฒนาการของซอฟต์แวร์)

1974 — Law of Continuing Change: ซอฟต์แวร์ต้องเปลี่ยนแปลง/วิวัฒน์ไปตามกาลเวลา
1974 — Law of Increasing Complexity: ต้องควบคุมความซับซ้อนที่เพิ่มขึ้นเรื่อยๆ
1974 — Law of Self-regulation: การกระจายตัวแบบปกติ (Normal distribution)
1980 — Law of Conservation of Organizational Stability: ความเสถียรของ Product Life Cycle
1980 — Law of Conservation of Familiarity: คงความคุ้นเคยในการใช้งานของซอฟต์แวร์ การเติบโตควรเป็นปกติ
1980 — Law of Continuing Growth: ฟังก์ชัน/รายละเอียดต้องค่อยๆ เพิ่มเพื่อรักษาความพึงพอใจ
1996 — Law of Declining Quality: คุณภาพจะไม่ลดลง หากดูแลบำรุงรักษาดีในสภาพแวดล้อมที่เหมาะสม
1996 — Feedback System Law: วงจรวิวัฒนาการของซอฟต์แวร์จะนำไปสู่การปรับปรุงที่ดีขึ้น

2. 7 Principles (หลักการสำคัญของ SE)

แนวข้อสอบ:

รีวิวรุ่นพี่ไม่เน้น Ch2 แต่หลักการ 7 ข้อเป็นหัวใจของบทนี้ มีสิทธิ์ออกเป็นจับคู่ (ชื่อหลักการ ↔ คำอธิบาย) จำ Keyword ให้ได้

จำโครงสร้าง 4 ชั้นของ SE: Tools ➜ Methodologies ➜ Methods/Techniques ➜ Principles (Principles เป็นฐานของทุกอย่าง)
คำศัพท์: Method = แนวทางปฏิบัติทั่วไป, Technique = เทคนิคเฉพาะเจาะจง, Method + Technique รวมกันเรียกว่า Methodology

1. Rigor and Formality (ความเคร่งครัดและความเป็นทางการ)

ทำงานอย่างเคร่งครัดเพื่อให้ได้ผลิตภัณฑ์ที่น่าเชื่อถือ ควบคุมต้นทุนได้ Formality คือขั้นสูงกว่า คือใช้กฎทางคณิตศาสตร์ขับเคลื่อนและประเมินกระบวนการ ส่งผลดีต่อ Reliability (ความน่าเชื่อถือ), Verifiability (ตรวจสอบได้ง่าย), Maintainability (บำรุงรักษาได้), Reusability (นำกลับมาใช้ใหม่), Portability (เคลื่อนย้ายได้), Understandability (เข้าใจง่าย), Interoperability (ทำงานร่วมกับระบบอื่น)

2. Separation of Concerns (การแยกข้อกังวล)

แยกประเด็น/ข้อกังวลออกจากกันเพื่อจัดการทีละอย่าง แยกได้หลายมิติ: Time (Life Cycle), Qualities (แยก Efficiency กับ Correctness), Views (มุมมองต่างกัน), Parts (ขนาด)

3. Modularity (การแบ่งโมดูล)

แบ่งระบบซับซ้อนเป็นชิ้นย่อย (Module) 2 เป้าหมาย: Decomposability (แบ่งจากบนลงล่าง Top-down / Divide and Conquer) และ Composability (ประกอบจากชิ้นส่วนย่อย Bottom-up)

4. Abstraction (นามธรรม)

มองเฉพาะสาระสำคัญ ซ่อนรายละเอียดที่ไม่จำเป็น (เป็นกรณีพิเศษของ Separation of Concerns) เช่น นาฬิกา = กล่องที่เปิดเปลี่ยนถ่านได้ โดยไม่ต้องรู้กลไกข้างใน

5. Anticipation of Change (การคาดการณ์การเปลี่ยนแปลง)

เตรียมพร้อมรับการเปลี่ยนแปลง 2 แบบ: แก้บั๊กที่ตรวจไม่เจอก่อนปล่อย และรองรับ Requirement ใหม่ที่เกิดขึ้นภายหลัง ➜ นำไปสู่ Evolvability และส่งผลต่อ Reusability อย่างมาก

6. Generality (ความทั่วไป)

ทำ Solution ให้ใช้ได้ทั่วไป (แต่ต้นทุนอาจสูงกว่าทำเฉพาะทาง ทั้งความเร็ว หน่วยความจำ และเวลา) เหมาะเมื่อเป้าหมายคือทำ General tools / packages ขายในตลาด

7. Incrementality (ความเป็นส่วนเพิ่ม)

ส่งมอบ "Early subset" (ส่วนย่อยที่ใช้ได้ก่อน) ให้ลูกค้าเพื่อรับ Early feedback เพราะไม่มีทางเก็บ Requirement ได้ถูกทั้งหมดตั้งแต่แรก ต้องคุมเอกสาร เวอร์ชัน และการเปลี่ยนแปลงอย่างเป็นระบบ

2. Methodology & Process Models

แนวข้อสอบ (Matching):

ทำความเข้าใจข้อจำกัดและลักษณะเด่นของแต่ละ Process Model ข้อสอบจะให้สถานการณ์งานมา แล้วให้จับคู่ว่า "งานแบบนี้เหมาะกับ Model ไหน"

Waterfall Model

แบบน้ำตก

ลักษณะ: ทำทีละเฟสให้เสร็จสมบูรณ์ วางแผนง่าย เอกสารชัดเจน (Requirements -> Design -> Code -> Test)

ข้อจำกัด: ลูกค้าเห็นระบบช้า แก้ไข Requirement ทีหลังทำได้ยากและแพง

เหมาะสำหรับ:

โครงการที่ความต้องการ (Requirements) นิ่งมาก, งานราชการ, งานที่เน้นเอกสารเป๊ะๆ

Prototyping Model

สร้างต้นแบบ

ลักษณะ: สร้างระบบจำลอง (Mockup) ขึ้นมาให้ลูกค้าดูก่อน เพื่อหาความต้องการที่แท้จริง

เหมาะสำหรับ:

โครงการที่ลูกค้ายังไม่แน่ใจว่าต้องการอะไร (Unclear requirements), เน้นการออกแบบ UI/UX ให้ลูกค้าจับต้องได้

Spiral Model

แบบก้นหอย

ลักษณะ: วนลูปการทำงานเป็นรอบๆ เน้นการวิเคราะห์ความเสี่ยง (Risk Analysis) ในทุกๆ รอบ

เหมาะสำหรับ:

โครงการขนาดใหญ่มาก (Huge Project), โครงการที่มีความซับซ้อนและมีความเสี่ยงสูงมาก (Mission-critical)

Incremental Model

เพิ่มทีละส่วน

ลักษณะ: แบ่งระบบเป็นส่วนย่อยๆ (Modules/Phases) พัฒนาและส่งมอบให้ลูกค้าใช้ทีละเฟส

เหมาะสำหรับ:

โครงการที่ต้องการให้ระบบหลัก (Core function) ออกไปใช้งานก่อน แล้วค่อยๆ ทยอยเพิ่มฟีเจอร์รองตามไปทีหลัง

Evolutionary Distribution Model

วิวัฒน์เป็นรุ่นๆ

ลักษณะ: พัฒนาและปล่อยเวอร์ชันแรกออกไปก่อน แล้วเก็บ Feedback จากผู้ใช้จริงมาปรับปรุง พัฒนาเป็นเวอร์ชันถัดไปเรื่อยๆ (Evolution)

ข้อจำกัด: เวอร์ชันแรกๆ ฟีเจอร์ยังไม่สมบูรณ์ ต้องวางแผนรองรับการเปลี่ยนแปลงและคุมเอกสาร/เวอร์ชันให้ดี

เหมาะสำหรับ:

ระบบที่ความต้องการเปลี่ยนไปตามกาลเวลา ต้องการ Feedback จากผู้ใช้เร็ว เพื่อค่อยๆ พัฒนาเวอร์ชันที่ดีขึ้นเรื่อยๆ

3. Software Quality (คุณภาพซอฟต์แวร์)

แนวข้อสอบ (Matching / เติมคำ):

ข้อสอบจะเป็นศัพท์ภาษาอังกฤษ ให้นิยามมาแล้วให้จับคู่หรือเติมคำให้ถูกต้อง (ต้องจำ Keyword ให้ได้)

1. Correctness (ความถูกต้อง)

โปรแกรมทำงานได้ถูกต้องตาม Functional Requirements ที่กำหนดไว้หรือไม่ ผลลัพธ์ถูกไหม

2. Reliability (ความน่าเชื่อถือ)

ความน่าจะเป็นที่ซอฟต์แวร์จะทำงานได้ตามที่คาดหวัง ใน ช่วงเวลาหนึ่งๆ (ไม่ค้าง ไม่ล่มบ่อย) ถ้าผลของความผิดพลาดไม่ร้ายแรง ซอฟต์แวร์ที่ทำงานไม่ถูกต้องบางจุดก็ยังถือว่า Reliable ได้

3. Robustness (ความทนทาน)

(ออกบ่อย)

ความสามารถในการรับมือกับ input ที่ผิดรูปแบบ (ill-formatted) หรือสถานการณ์ที่ไม่คาดคิด โดยระบบไม่พัง

4. Performance (ประสิทธิภาพ)

เกี่ยวข้องกับความเร็ว (Speed) การประมวลผล และขนาดหน่วยความจำที่ใช้ (Memory usage)

5. User Friendly (ความเป็นมิตรต่อผู้ใช้)

เรียนรู้และใช้งานง่าย (Usability) มี User Interface ที่ดี ตอบสนองการทำงานของผู้ใช้ได้สะดวก

6. Verifiability (ความสามารถในการตรวจสอบได้)

ระบบควรถูกตรวจสอบ (Verify) ได้ง่าย เทคนิคคือแทรก Software Monitors — โค้ดที่ฝังไว้ในซอฟต์แวร์เพื่อมอนิเตอร์ Performance/Correctness เป็นได้ทั้ง Internal & External quality

7. Maintainability (การบำรุงรักษาได้)

(ออกบ่อย)

ความง่ายในการบำรุงรักษา/วิวัฒน์ แบ่งเป็น 3 แบบ: Corrective (แก้ Error ที่เพิ่งเจอตอนส่งมอบ), Adaptive (ปรับตาม Environment เช่น OS/DB ใหม่), Perfective (เพิ่มฟังก์ชัน/ปรับปรุงคุณภาพ)

8. Repairability (ความง่ายในการซ่อมแซม)

มาจากแนวคิด RAS (Repairability, Availability, Serviceability) ใช้ชิ้นส่วนมาตรฐาน (Standard parts) ลดต้นทุน ซ่อมส่วนเดียวแทนทั้งระบบ โมดูลที่ออกแบบดี + Interface ที่ดีช่วยลดการเชื่อมโยงระหว่างโมดูล

9. Evolvability (ความสามารถในการวิวัฒน์)

ซอฟต์แวร์ถูกแก้ไขตามเวลาเพื่อเพิ่ม/เปลี่ยนฟังก์ชัน ถ้าไม่บันทึกการแก้ไขจะแก้ในอนาคตยาก ต้องศึกษาดีไซน์เดิมอย่างรอบคอบ และบันทึกการเปลี่ยนแปลงทั้ง Design และ Requirements Specification ให้แม่นยำ

10. Reusability (การนำกลับมาใช้ใหม่)

ปรับแต่งผลิตภัณฑ์เพื่อสร้างเวอร์ชันใหม่ หรือนำชิ้นส่วน (Requirements, Design, Code) ไปใช้กับผลิตภัณฑ์อื่น โดยแก้ไขเล็กน้อย เพื่อลดต้นทุนการผลิต

11. Portability (ความสามารถในการเคลื่อนย้าย)

ความสามารถในการรันระบบบน Environment/Platform (OS) ที่แตกต่างกัน ได้ เช่น รันได้ทั้งบน Windows และ macOS

12. Understandability (ความสามารถในการเข้าใจได้ง่าย)

Design ที่อ่านแล้วเข้าใจง่าย เป็น Internal quality และเป็นตัวช่วยสำคัญให้บรรลุ Evolvability และ Verifiability

13. Interoperability (การทำงานร่วมกันได้)

ความสามารถของระบบในการอยู่ร่วม (Coexist) และทำงานร่วม (Cooperate) กับระบบอื่น เช่น ผลิตภัณฑ์จากหลายผู้ผลิตที่รวมฟังก์ชันต่างกันเข้าด้วยกัน

14. Productivity (ความสามารถในการผลิต)

เป็นคุณภาพของ Process (ไม่ใช่ Product) การนำกลับมาใช้ใหม่ (SW Reuse) ช่วยเพิ่ม Productivity ขององค์กร แต่การสร้างโมดูลที่ Reuse ได้ทำยากกว่าสร้างใช้เอง

15. Timeliness (ความตรงต่อเวลา)

คุณภาพของ Process คือความสามารถในการส่งมอบผลิตภัณฑ์ได้ตรงตามเวลา

16. Visibility (ความโปร่งใส/มองเห็นได้)

กระบวนการพัฒนาโปร่งใส ถ้าทุกขั้นตอนและสถานะปัจจุบันถูกบันทึกไว้ชัดเจน เป็นได้ทั้ง Internal & External quality ช่วยให้วิศวกรประเมินผลกระทบของการกระทำและตัดสินใจได้ดีขึ้น

เสริม Ch3: Quality Requirements ของระบบ 4 ประเภท

สไลด์ยกตัวอย่างว่าแต่ละแอปพลิเคชันเน้นคุณภาพด้านไหน ข้อสอบจับคู่ "ระบบแบบไหน → คุณภาพอะไรสำคัญ"

1. Information Systems

เช่น Banking, Library, Personnel — หัวใจคือ Database (Create/Retrieve/Update/Delete)

  • Data integrity — ข้อมูลจะถูกทำลายไหม?
  • Security — ป้องกันการเข้าถึงโดยไม่ได้รับอนุญาต
  • Data availability — เงื่อนไขใดข้อมูลจึงใช้ไม่ได้
  • Transaction performance — รองรับธุรกรรมกับข้อมูล

2. Real-Time Systems

เช่น ระบบเฝ้าระวังโรงงาน, Mouse-handling Software

  • ต้องตอบสนอง Event ภายในเวลาที่กำหนดตายตัว
  • ตอบเร็วเกินไปก็ผิด (เช่น Double-click ตรวจไม่เจอถ้าประมวลผล Click แรกเร็วเกิน)
  • คุณภาพวัดที่ Response Time ซึ่งเป็นหนึ่งในเกณฑ์ของ Correctness

3. Distributed Systems

Component รันบนคอมพิวเตอร์หลายเครื่อง

  • ทนต่อ Network Partitioning (สื่อสารกันไม่ได้บางช่วง)
  • ทนต่อความล้มเหลวของคอมพิวเตอร์บางเครื่อง
  • ทำ Replication (เก็บข้อมูลซ้ำหลายเครื่อง) เพิ่ม Reliability

4. Embedded Systems

เช่น เครื่องบิน, หุ่นยนต์, ไมโครเวฟ, ตู้หยอดเหรียญ, เครื่องติดตามผู้ป่วย

  • SW เป็นหนึ่งในหลาย Component มักไม่มี Interface ให้ผู้ใช้
  • Interface เชื่อมต่อกับอุปกรณ์อื่นมากกว่ามนุษย์

4. Tasks of Software Development (Ch4)

แนวข้อสอบ:

Verification vs Validation คือจุดตายที่ออกแน่ๆ (ดูด้านล่าง) แต่กิจกรรมอื่นใน Ch4 อย่าง Feasibility Study, Documentation, Design ก็ถูกเอามาถามได้ในข้อจับคู่ ให้จำ "ชื่อกิจกรรม ↔ ผลลัพธ์ (Product)" ให้ได้

13 กิจกรรมใน Software Development

1. Feasibility Study

กิจกรรมแรก ตัดสินใจว่าโครงการควรเดินต่อหรือไม่ (ระบบไม่จำเป็น / แพงเกิน / เสี่ยงเกิน) ใช้ Cost-Benefit Analysis เทียบต้นทุนกับผลตอบแทนที่คาดหวัง

2. Requirements Engineering

หาความต้องการของผู้ใช้ (Client/Customer) แล้วบันทึกให้ชัดเจน ผลลัพธ์ = Requirements Specification

3. User Interface Design

ออกแบบ UI ให้ใช้งานง่าย ส่วนใหญ่เป็น Graphical User Interface (GUI)

4. Architectural Design

ออกแบบภาพใหญ่ (Large-scale) — แบ่งระบบใหญ่เป็น Modules/Components ผลลัพธ์ = Architectural design + Module specifications

5. Detailed Design

ออกแบบภายในของแต่ละโมดูล ผลลัพธ์ = Detailed designs ของทุกโมดูล

6. Programming (Coding)

แปลง Design เป็นคำสั่งในภาษาโปรแกรม (ต้องเลือกภาษาให้เหมาะ) ผลลัพธ์ = Code

7. System Integration

ประกอบชิ้นส่วนย่อยเข้าด้วยกัน (เรียกว่า The Build) ผลลัพธ์ = Complete system

8. Verification

ตรวจว่าระบบถูกสร้างถูกต้อง (Developer's view) ประกอบด้วย Unit Testing + System Testing ↓ ดูรายละเอียดด้านล่าง

9. Validation

ตรวจว่าระบบตรงความต้องการผู้ใช้ (Client's view) ตัวอย่างสำคัญคือ Acceptance Testing ↓ ดูรายละเอียดด้านล่าง

10. Production

นำระบบไปใช้งานจริง (บางครั้งเรียก Implementation) ผู้ใช้อาจต้องเข้ารับการอบรม (Training)

11. Maintenance

แก้ไข/เพิ่มเติมซอฟต์แวร์หลังใช้งานจริง มักกินเวลาหลายปี ผลลัพธ์ = Modified software

12. Documentation

เอกสาร 2 กลุ่ม — User (วิธีติดตั้ง/ใช้งาน เน้น "what" มุมมองภายนอก) และ Developer (specification, design, code, comments, test schedules/results, project plan)

13. Project Management

สร้าง/ดูแลแผนงาน แก้ปัญหา มอบหมายงาน และตรวจว่างานเสร็จ — เนื้อหาละเอียดอยู่ใน Ch5

จุดตายข้อสอบ (ห้ามพลาด!)

"สามารถแก้ไขซอฟต์แวร์ได้แบบ static Verification"

คำอธิบาย: Static Testing (การทดสอบสถิต เช่น การรีวิวโค้ด หรือตรวจเอกสาร โดยที่ไม่ได้รันโค้ด) จัดอยู่ใน Verification
ส่วน Validation มักจะเป็น Dynamic Testing (รันโปรแกรมจริงเพื่อให้ลูกค้าตรวจรับระบบ - Acceptance Testing)

1

VERIFICATION

"Are we building the product right?"
(เราสร้างระบบอย่างถูกต้องตามเอกสารไหม?)

  • มุมมองของฝั่ง ผู้พัฒนา (Developer's view)
  • เช็คการทำงานภายใน (Internal implementation) โค้ดเขียนถูกไหม
  • ตัวอย่าง: Unit Testing (ทดสอบรายโมดูล)

อุปมาอไมย

เสื้อตัวนี้มี 2 แขนไหม? ไซส์ L ไหม? กระดุมครบไหม? (เช็คตามใบสั่งตัด)

2

VALIDATION

"Are we building the right product?"
(เราสร้างระบบที่ตรงใจลูกค้าจริงๆ ไหม?)

  • มุมมองของฝั่ง ลูกค้า/ผู้ใช้งาน (Client's view)
  • ดูว่าซอฟต์แวร์ตอบโจทย์การใช้งานทางธุรกิจจริงๆ หรือไม่
  • ตัวอย่าง: Acceptance Testing (ทดสอบตรวจรับงาน)

อุปมาอไมย

เสื้อตัวนี้ใส่พอดีไหม? ใส่ขับรถสบายไหม? สีเข้ากับผิวฉันไหม? (ตอบโจทย์ชีวิตไหม)

ติวอัตนัย: บทบาท Project Manager

Question:

ถ้านักศึกษาเป็น Project Manager ของ Term Project ต้องทำให้โปรเจกต์สำเร็จด้วยหลักการใด อธิบายในรายละเอียด

แนวทางการเขียนตอบ: ให้ยึดสามเหลี่ยมข้อจำกัด (Quality, Cost, Delivery) และกระบวนการบริหารจัดการ 4 ขั้นตอน

หากผมได้รับบทบาทเป็น Project Manager (PM) เพื่อบริหาร Term Project ให้ประสบความสำเร็จ ผมจะประยุกต์ใช้ หลักการจัดการโครงการ (Project Management Principles) โดยต้องควบคุมข้อจำกัด 3 ด้าน คือ Quality (คุณภาพ), Cost (ทรัพยากร/แรงงาน), และ Delivery/Time (เวลา) ผ่านกระบวนการ 4 ขั้นตอน ดังนี้:

1. การวางแผน (Planning)

คือขั้นตอนที่สำคัญที่สุด ผมจะเริ่มจากการกำหนดขอบเขต (Scope) ของระบบ จากนั้นแบ่งย่อยงาน (Work Breakdown Structure - WBS) เพื่อให้ประเมินเวลาง่ายขึ้น และจะใช้ Gantt Chart ในการจัดตารางเวลา (Schedule) ให้เห็นลำดับงานชัดเจน รวมถึงประเมินความเสี่ยง (Risk Management) ล่วงหน้า เช่น เทคโนโลยีที่ไม่คุ้นเคย หรือช่วงเวลาสอบที่สมาชิกไม่ว่าง

2. การจัดโครงสร้างและบุคลากร (Organizing & Staffing)

แบ่งหน้าที่ (Role & Responsibility) ตามความถนัดของเพื่อนในทีม เช่น Frontend, Backend, Database ทรัพยากรหลักของงานนักศึกษาคือ "ทักษะและเวลา" การจัดคนให้ตรงกับงาน (Put the right man on the right job) จะช่วยลดเวลาพัฒนาและเพิ่มคุณภาพของงานได้สูงสุด

3. การสั่งการและสื่อสาร (Directing)

ขับเคลื่อนทีม (Drive) และกำหนดเป้าหมายร่วมกัน หัวใจหลักคือ "การสื่อสาร" ผมจะจัดให้มีการอัปเดตงานอย่างสม่ำเสมอ เพื่อลดความเข้าใจผิดของ Requirement และพร้อมเข้าช่วยเหลือ (Support) หากสมาชิกติดปัญหา Technical

4. การควบคุม (Controlling)

มอนิเตอร์ความคืบหน้าเทียบกับแผน (Gantt Chart) หาก Task ใดเกิดคอขวด (Delay) ต้องรีบปรับเปลี่ยนแผน (Corrective Action) เช่น ดึงคนมาช่วยทำ และกำกับให้ทีมทำ Verification (เช่น Unit Testing) เพื่อควบคุมให้คุณภาพซอฟต์แวร์ตรงตามสเปคก่อนส่งมอบให้อาจารย์

เสริม Ch5: เครื่องมือวางแผน & ควบคุมโครงการ (ออกข้อจับคู่)

WBS (Work Breakdown Structure)

แบ่งงานใหญ่ออกเป็นงานย่อยเป็นลำดับชั้น (เช่น Software Development → Requirement Definition / Design / Development / Integrate Testing / Project Management) เพื่อประเมินเวลา-ทรัพยากรได้ง่าย

Gantt Chart

แผนภาพแท่งแสดงว่างานแต่ละชิ้นเริ่ม-จบเมื่อไร (Henry L. Gantt, 1917) ข้อจำกัด: ไม่แสดงความสัมพันธ์ระหว่างงาน ไม่บอกผลกระทบถ้างานล่าช้า และไม่เหมาะกับโปรเจกต์ใหญ่ที่ซับซ้อน

PERT (Program Evaluation and Review Technique)

เน้นเวลา (Time) เหมาะกับโปรเจกต์ใหญ่ ใช้ Network Diagram แบบ AOA (Activity On Arrow) เพื่อดูความสัมพันธ์และลำดับงาน

CPM (Critical Path Method)

เน้นต้นทุน (Cost) ใช้หา Critical Path — เส้นทางงานที่ถ้าล่าช้าจะกระทบเวลารวมของโครงการ

Milestones vs Deliverables

Milestones = จุดสิ้นสุดของแต่ละ Process Activity (ใช้วัดความคืบหน้า) / Deliverables = ผลงานที่ส่งมอบให้ลูกค้า (เช่น Feasibility report, Requirements definition)

Project Life Cycle

Initiation (กำหนดขอบเขต/ขนาดงาน) → Planning (วางแผนงาน-เวลา-ความเสี่ยง) → Execution (ลงมือทำตามแผน) → Closing (ปิดโครงการ — สำเร็จหรือล้มเหลว)

ติวอัตนัย: การวิเคราะห์ระบบ CS-Hospital

แนวข้อสอบ:

ข้อเขียนให้ "เขียน FR และ NFR จากโจทย์ระบบ" — อ่านทฤษฎีด้านล่างให้จบ แล้วค่อยดูตัวอย่างเฉลย CS-Hospital และฝึกทำแนวข้อสอบท้ายบท

ประเภทของ Requirements (Ch6)

  • Functional Requirements (FR) — ฟังก์ชันทางธุรกิจที่ผู้ใช้จะใช้ทำงานกับระบบ (สิ่งที่ระบบต้องทำได้)
  • Non-Functional Requirements (NFR) — ข้อกำหนดด้านคุณภาพ/ข้อจำกัดของระบบ ครอบคลุมด้วย FURPS+
  • User Interface Requirements — ข้อกำหนดเกี่ยวกับหน้าตา/การใช้งาน UI

FURPS+ = 5 หมวดของ NFR (ต้องจำได้)

F — Functionality (รวม Security ความปลอดภัย!)
U — Usability ใช้งานง่าย
R — Reliability เชื่อถือได้ ไม่พังบ่อย
P — Performance เร็ว ใช้ทรัพยากรคุ้มค่า
S — Supportability บำรุงรักษา/ติดตั้ง/พกพาได้

จุดหลอกข้อสอบ: ในสไลด์ "Security" ถูกจัดอยู่ในหมวด Functionality ไม่ใช่ Reliability!

วิธีแยก FR กับ NFR (เทคนิคทำข้อสอบ)

FR ตอบคำถาม "ระบบทำอะไรได้บ้าง?"

รูปประโยค: "ระบบต้องสามารถ + คำกริยา" (บันทึก, ค้นหา, พิมพ์, ส่งต่อ, ออกรายงาน)

ตัวอย่าง: พิมพ์ใบรับรองแพทย์ได้ / ส่งผลวินิจฉัยผ่าน LINE ได้

NFR ตอบคำถาม "ระบบดีแค่ไหน / มีเงื่อนไขอะไร?"

มักมีตัวเลข ช่วงเวลา หรือคำขยาย: ไม่เกิน 3 วินาที, 99.9%, ตลอด 24 ชม., ปลอดภัย, ใช้งานง่าย

ตัวอย่าง: พร้อมใช้งาน 99.9% / ค้นหาผู้ป่วยภายใน 3 วินาที

สูตรเขียนตอบข้อเขียน (ใช้ได้กับทุกโจทย์)

  1. อ่านโจทย์แล้วขีดเส้นใต้ทุกฟังก์ชันที่โจทย์บอก → เขียนเป็น FR ทีละข้อ (1 บรรทัดโจทย์ = อย่างน้อย 1 FR)
  2. FR ต้องครอบคลุมโจทย์ครบทุกบรรทัด — ถ้าตกบรรทัดไหน = เสียคะแนน
  3. NFR เลือกจาก 5 หมวด FURPS+ อย่างน้อย 3-4 ข้อ และใส่ตัวเลข/ช่วงเวลาให้จับต้องได้ (เช่น 99.9%, ไม่เกิน 3 วินาที, 24 ชม., รองรับ 100 คนพร้อมกัน)
  4. FR ใช้คำกริยา "ระบบต้องสามารถ..." / NFR ใช้ "ระบบต้องมี/ต้องใช้งานได้..." + ตัวเลข

ความรู้ประกอบข้อจับคู่ Ch6

RE 3 Components

Gathering (Elicitation — เก็บความต้องการ) → Analysis (กลั่นกรอง/ปรับปรุง) → Specification (เขียนเป็นเอกสารให้ชัดเจน)

User Story

"As a role, I can capability so that business-goal" — เขียนโดยลูกค้า/ผู้ใช้ นิยมใช้ใน Agile

Acceptance Tests

ลูกค้าเป็นผู้ทดสอบ ตลอดทั้งโปรเจกต์ (ไม่ใช่แค่ตอนจบ) เป็นตัวชี้วัดว่า Requirement ถูกทำสำเร็จ

โจทย์: เขียน Functional Requirement (FR) และ Non-Functional (NFR)

"โรงพยาบาลขนาดเล็กแห่งหนึ่ง เปิดให้นักศึกษา และบุคลากรในสถาบัน และเปิดรับผู้ป่วยนอกทั่วไปด้วย แต่ยังไม่มีระบบจัดการผู้ป่วย จึงอยากให้นักศึกษาออกแบบเว็บแอปพลิเคชันจัดการผู้ป่วย โดยมีการทำงานดังนี้:
- สามารถเก็บข้อมูลผู้ป่วย เช่น ประวัติการรักษา ผลการรักษา ผลจากห้องปฏิบัติการ
- สามารถเก็บข้อมูลบุคลากรทางการแพทย์
- สามารถออกรายงานต่างๆ เช่น ใบรับรองแพทย์ ประวัติการรักษา
- สามารถส่งต่อผลการรักษาหรือผลการวินิจฉัยไปให้ทีมแพทย์ผู้เชี่ยวชาญ หรือทีมอื่นที่เกี่ยวข้องกับโรคเฉพาะทาง ผ่านช่องทางออนไลน์ เช่น LINE หรือ Email"

1. Functional Requirements (สิ่งที่ระบบต้องทำได้)

  • 1.1 ระบบจัดการข้อมูลผู้ป่วย (Patient Management)

    - ระบบต้องสามารถเพิ่ม ลบ แก้ไข ค้นหาข้อมูลส่วนตัวของผู้ป่วย (นักศึกษา, บุคลากร, ผู้ป่วยนอก) ได้

    - ระบบต้องสามารถบันทึกประวัติการรักษา ผลการรักษา และผลแล็บ (Lab results) เข้าสู่ฐานข้อมูลได้

  • 1.2 ระบบจัดการข้อมูลบุคลากรทางการแพทย์ (Staff Management)

    - ระบบต้องสามารถบันทึกและจัดการข้อมูลโปรไฟล์ของแพทย์ พยาบาล และเจ้าหน้าที่ได้

  • 1.3 ระบบสร้างรายงาน (Reporting System)

    - ระบบต้องสามารถดึงข้อมูลมาสร้างและพิมพ์ประวัติการรักษาของผู้ป่วยได้

    - ระบบต้องสามารถสร้างแบบฟอร์มใบรับรองแพทย์และสั่งพิมพ์หรือบันทึกเป็น PDF ได้

  • 1.4 ระบบส่งต่อข้อมูลและการแจ้งเตือน (Referral & Notification)

    - ระบบต้องสามารถส่งต่อข้อมูลเคสการรักษาให้ทีมแพทย์ผู้เชี่ยวชาญได้

    - ระบบต้องเชื่อมต่อ API เพื่อส่งข้อความแจ้งเตือนผลวินิจฉัยไปยังแอปพลิเคชัน LINE หรือ Email ได้

2. Non-Functional Requirements (คุณภาพของระบบ)

  • 2.1 ความปลอดภัย (Security & Privacy)

    - ข้อมูลคนไข้เป็นความลับ ระบบต้องมีการเข้ารหัสข้อมูล (Encryption) และต้องยืนยันตัวตน (Login) ก่อนเข้าใช้งาน

    - ต้องมีการแบ่งสิทธิ์ผู้ใช้ (Authorization) เจ้าหน้าที่ทั่วไปห้ามเห็นบันทึกการวินิจฉัยเชิงลึกของแพทย์

  • 2.2 ความพร้อมใช้งาน (Availability)

    - ระบบโรงพยาบาลควรมีความพร้อมใช้งานสูง 99.9% Uptime รองรับเหตุฉุกเฉินตลอด 24 ชั่วโมง และต้องมีการ Backup ข้อมูลทุกวัน

  • 2.3 ประสิทธิภาพ (Performance)

    - การสืบค้นประวัติผู้ป่วยจากฐานข้อมูลต้องใช้เวลาแสดงผลไม่เกิน 3 วินาที เพื่อความรวดเร็วในการรักษา

  • 2.4 ความสามารถในการพกพา (Portability)

    - เว็บแอปพลิเคชันต้องเป็นแบบ Responsive สามารถใช้งานได้ดีทั้งบน PC และแท็บเล็ต (Tablet) สำหรับแพทย์ที่เดินตรวจวอร์ด

แนวข้อสอบปี 67 (รหัส 66): ระบบนักศึกษา

ออกแนวเดียวกัน เปลี่ยนโจทย์เป็น "ระบบจัดการข้อมูลนักศึกษา" ให้ใช้แพตเทิร์นเดียวกับ CS-Hospital:

  • FR (สิ่งที่ระบบต้องทำ): ลงทะเบียนเรียน, ตรวจสอบผลการเรียน/เกรด, จัดการข้อมูลส่วนตัวนักศึกษา, ออกเอกสารรับรอง/Transcript, แจ้งเตือนข่าวสาร
  • NFR (คุณภาพของระบบ): ความปลอดภัยของข้อมูลส่วนตัว, รองรับผู้ใช้พร้อมกันมากช่วงลงทะเบียน (Performance), ใช้งานได้ตลอดเวลา (Availability), ใช้งานผ่านมือถือได้ (Portability)
